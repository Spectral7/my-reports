1 The short version

What he actually has

One sentence: a complete, self-consistent safety system for running a company on AI agents — built for money-grade stakes, and only three days old.

Bottom line

Shakhzod has built 13 small tools that together form one loop, not a pile of utilities. Each one guards a specific way an AI agent can lie to you: it says the deploy worked (it didn't), it approves its own bad code, it remembers an approval that expired last month, it fixes the wrong side of a contradiction while you sleep. Every tool is free to take (CC0 public domain), has zero dependencies, and installs in one command.

The honest caveat: everything was published on 13–14 July 2026 — two to three days ago. All are version 1.0.0. Zero stars, zero forks, one author. Roughly half of them are prompts, not programs — the "tool" is a page of rules the AI reads. That is not a criticism; the rules are the product. But it means you can adopt most of this by reading it, not installing it.

His pitch

His six operating principles, verbatim from his profile: "One writer per worktree. A second, independent model attacks meaningful diffs. 'Done' is checked at the system of record. Handoffs carry receipts. Unattended agents file, don't fix. The loop matters more than the prompt."

Those six sentences are the entire collection in miniature — each one is a tool. And his background explains the collection's centre of gravity: this is a fraud-and-payments person's view of AI agents. A fraud specialist's instinct is that a claim is not evidence, that you check the system of record rather than the story, and that the expensive failure is the one that looks fine. Every tool here is built on that instinct.

Read this bias before you adopt anything

He is optimising for real money moving under an agent's control. His phrase, repeated in nearly every repo, is "production stakes." That is a genuinely different risk profile from yours. Some of what he built is essential for a regulated lender and pure ceremony for a one-person operation — and the report flags which is which.

3 The organising idea

It's a loop, not a toolbox

This is the thing to understand. Everything else is detail.

He published a 14th repo called agent-stack whose only job is to be the map. It contains no code — just a README and a routing table. Its first line sets the frame:

agent-stack, verbatim

"The runsagents agent stack: how one human runs a company where agents do the work. Every piece assumes production stakes: real money, real state, real consequences."

"This is a control loop, not a toolbox shelf."

Read left to right, top row then bottom row. In plain language:

  1. Give each agent its own sandbox so two agents can't overwrite each other's work.
  2. Have a different AI attack the code — the model that wrote it can't see its own blind spots.
  3. Check the real system, not the agent's report, before believing "done."
  4. Write a receipt when work changes hands, carrying the risks that are still open.
  5. Sort the open questions by what being wrong would cost — not by what feels uncertain.
  6. The human decides. This is the centre. Everything upstream exists to make this decision well-informed; everything downstream exists to keep it honest.
  7. Quiz the human so they can still answer for code the agents wrote.
  8. Then: store memory with an expiry date, let overnight agents report but never fix, and price your model choices from real outcomes.
The one design decision underneath all of it

Every single tool refuses to make the decision itself. Not one of them merges, deploys, fixes, approves, or acts. They gather evidence and hand it to a person. agent-fleet-control never commits or merges. night-watch can only file findings, never fix. settlement-proof "does not repair, retry, reverse, refund, or post." loss-weighted-unknowns "does not approve a release." permission-surface "never certifies safe."

This is the actual thesis of the collection, and it is worth more than any individual tool: as agents get more capable, the scarce resource is not agent work — it's a human who still understands enough to be accountable. Every tool protects that human's ability to decide.

Discipline

5 tools · the core loop

His largest family. These are the tools that run every time an agent writes code, regardless of what the code does.

agent-fleet-control
Bash · 20/20 testsv1.0.0

One writer per worktree. Each agent gets its own copy of the repo, its own branch, and a declared list of folders it's allowed to touch — and the tool refuses to create two agents whose folders overlap.

Problem
Two agents in one folder overwrite each other. Both honestly report success; the final code matches neither of the things they verified.
Mechanism
A single 580-line Bash script, four commands: new (create agent + worktree + contract), verify (run its test command and capture the output as tamper-checked evidence), receipt (produce a merge receipt for a human), help.
Clever bit
Evidence is bound to an exact commit and hashed. If the code changes after verification, the receipt is refused: "verification does not cover the current commit." It also detects if your test command dirtied the repo and forces exit code 125.
Install
Clone, then copy one file to your $PATH. No dependencies at all — just Bash and Git.
Reality check
Only tested on macOS. Linux, WSL, Git Bash are all explicitly marked "Untested." The bundled policies/default.yaml is never read by any code — it's decoration.
His limitation, verbatim: "Path ownership is coordination metadata. It does not prevent a process from writing outside its territory; the agent host or OS sandbox must enforce that separately." — and: "It never commits, pushes, or merges."
second-opinion
4/4 testsv1.2.0

A different AI, from a different vendor if possible, is briefed to attack your code. Not to review it — to prove it wrong.

Problem
His line: "Same model writing and reviewing is homework marking itself." The model that wrote the code reviews it with the same assumptions that produced the bug.
Mechanism
Four steps: collect the diff → brief the other model → one rebuttal round → escalate. The briefing is fixed text: "This code was written by another AI. Your job is to prove it wrong."
Key rule
Do not show the reviewer the author's reasoning — it anchors them. And: exactly one rebuttal round, because "more rounds means the models negotiate; you don't want them to."
Outcome
Reviewer says clear → pass. Says objection → author may concede (fix it) or stand (escalate). A standing disagreement always goes to a human. "NEVER resolve a standing disagreement silently."
Install
npx skills add runsagents/second-opinion. Requires a second model you can reach — a second CLI, an API, or another agent session.
Reality check
The "code" is an 81-line script that pretty-prints two JSON files you write by hand. It does not detect disagreement — it formats it. The product is the ritual.
His limitation, verbatim: "Costs a second model call per review... Two models agreeing is strong evidence, not proof; keep your tests and gates. And never let the models resolve a disagreement between themselves: that's negotiation, not review."
airlocks
Prompt-first3/3 testsv1.1.0

The most quotable tool in the collection, and one of the most useful. When an agent says "done," you check the real system before believing it.

Origin story
Worth quoting in full: "An agent once told me a deploy succeeded. Its evidence: the word 'success' appeared in the logs. It appeared inside an error message. The broken build reached TestFlight."
The five rules
1. Words are claims, state is evidence. 2. Never grep for success words — parse exit codes. 3. Ask the system of record, not the actor. 4. The doer never verifies its own work. 5. On mismatch, halt and report — file, don't fix.
How to check
Merged? git merge-base --is-ancestor. Deployed? The platform API reports the new build number. Tests pass? Run them on the merged commit, not the branch. Fixed? Reproduce the original failure and watch it not happen.
Report format
Four lines, always: CLAIM / SYSTEM OF RECORD / EVIDENCE / VERDICT (CONFIRMED · REFUTED · UNVERIFIABLE).
Install
npx skills add runsagents/airlocks, then say "airlock this."
Reality check
The whole product is a 34-line rulebook. The demo script is a hardcoded illustration, exports nothing, and can't be imported. It also always exits 0 — even when it REFUTES — so it can't gate a pipeline as shipped.
His limitation, verbatim: "Some claims are genuinely unverifiable from your seat (say so, don't guess). Airlocks catch false 'done's; they don't catch wrong designs, that's what review is for." — Tagline: "agents don't need supervision. They need airlocks."
handoff-receipts
11/11 testsv1.0.0

Work changing hands must carry a structured receipt — and the receiver refuses work that arrives without one.

Problem
An agent handed off a clean summary that quietly omitted one unresolved deployment risk. The receiver trusted the green test line and lost a day. His point: "the handoff simply had no required place for the uncomfortable fact."
The seven fields
task & scope · territory (which paths you were allowed to touch) · decisions + why · unresolved risks · verification (command, exit code, output) · artifacts · acceptance checklist.
Clever bit
Verification status can be passed, failed, or not-run. "We didn't check" is a first-class, recordable state — it can't hide as silence.
The actual rule
"No receipt, no acceptance." The validator is secondary; this social rule is the product.
Install
Clone. Node ≥18. Zero dependencies.
Reality check
Structure only. Nothing stops a sender pasting fabricated command output into a structurally perfect receipt.
His limitation, verbatim: "Validation checks structure, not whether a claim or pasted command output is true." — repeated in four separate places: "validation is not proof."
night-watch
Prompt-first5/5 testsv1.0.0

Scheduled agents inspect the repo read-only and file findings. They are categorically forbidden from fixing anything.

Origin story
The best failure story in the collection: "An unattended fixer found a mismatch between a guide and the runtime. The guide described the intended behavior; the runtime contained a bug. With no human awake to decide which side was authoritative, the agent confidently 'corrected' the guide to match the bug. The repository woke up internally consistent and more wrong."
Four checks
citations (do the links in docs actually support the claims?) · dead-branches (unreachable code) · docs-vs-code (docs contradict reality) · invariants (rules the code states but can break).
Finding format
WHAT · WHERE · EVIDENCE · SUGGESTED-OWNER — the human who can decide intent. The finding deliberately doesn't say which side is wrong. That's the whole doctrine.
Design highlight
Each check spends as much text on what not to file as what to file. Best line: "A network failure is not proof of a dead citation."
Reality check
"File, don't fix" has zero code enforcement — it's a prompt asking the model to police itself. Whether it holds depends entirely on your permission settings, not this repo.
His limitation, verbatim: "Checks are agent instructions, not deterministic analyzers... A valid packet proves that required fields are present and well-formed; it does not prove that the conclusion is correct. Human triage remains necessary."

Money stakes

2 tools · the fintech core

Where his day job shows most clearly. These two have the most real code and the narrowest fit.

settlement-proof
7/8 tests — REDv1.0.0

"The payment airlock for AI agents that touch real money." Blocks a payment "done" claim until four independent systems agree.

Problem
An agent got a SETTLED response from the processor and declared the payment done. The internal ledger contained no entries at all.
The four systems
Processor (the provider says it settled) · Ledger (double-entry records exist and sum to zero) · Idempotency store (exactly one effect applied; every retry accounted for) · Reconciliation (a completed match exists).
Two policies
Fail fast on contradiction (halt immediately, mark the rest NOT_EVALUATED) and fail closed on absence (missing evidence blocks — absence is never permission). Three verdicts map to three exit codes: PROVED=0, MISMATCH=1, UNVERIFIABLE=2.
Best detail
"Compensation is evidence, not a fifth source allowed to overrule disagreement among the four." This is enforced structurally — the schema literally has no slot for compensation to halt on. He built the rule into the data shape, not just the prose.
Reality check
Ships zero integrations. You build every adapter yourself. Its real prerequisite is a payments architecture mature enough that the tool is nearly redundant.
His limitation, verbatim (an entire shouted section titled WHAT IT DOES NOT PROVE): "...the customer authorized the payment or received the goods; the merchant, tax treatment, fee model or business decision was correct; funds are irrevocable... The packet proves only the bounded agreement encoded by the v1 checks over the supplied snapshot."
route-ledger
4/4 testsv1.0.0

Which AI model is cheapest? Not the one with the lowest token price — the one that costs you least after you count the human time spent fixing its output.

The formula
Real cost = tokens + human review minutes + correction minutes + reruns + an expected-loss proxy (a $ figure per defect severity: none $0 / minor $2 / major $25 / critical $250). Ranked by cost per accepted run — rejected work isn't output.
The killer number
In his own 40-run demo: token spend is 0.1% of total cost. Human review is 72%, corrections 27%. The entire ranking is decided by human minutes. That single statistic is arguably the most valuable thing in the repo.
Refuses to guess
Needs ≥5 runs per model-per-task and ≥80% acceptance, or it returns NO RECOMMENDATION. One of his three demo categories deliberately gets exactly that.
Reality check
It's a calculator, not a collector — you build the logging. To reach "high confidence" on 3 models × 3 task types you need 270+ labelled runs. And it needs a timed human review step; a fully automated pipeline has nothing to feed it.
His limitation, verbatim: "Expected loss is a proxy: severity weights are assumptions and can dominate the ranking. Run sensitivity analysis." — and: "Do not use this report as the sole control for safety-, credit-, compliance-, or other high-stakes production decisions."

Measurement

2 tools · prove it works

The most intellectually honest part of the collection — one of these exists purely to test whether another one of his own tools is worth using.

second-opinion-bench
10/10 tests · best-testedv1.1.0

Twelve deliberately planted bugs. Give them to your reviewers, see who catches what, and measure whether a second model actually adds anything.

Why it exists
To falsify his own second-opinion skill. Its stated problem: "A second reviewer can add cost without catching defects the first reviewer missed." He built the tool that could prove his other tool worthless.
The corpus
12 fixtures, 2 in each of 6 classes: logic errors, missing edge cases, security slips, money-rounding bugs, concurrency hazards, silent behaviour changes. Every one is a plausible refactor that silently regresses — none look like sabotage.
Example bugs
A one-token change flipping a retry default from true to false. parseInt("12.34") silently dropping every sub-dollar part of a fee. An atomic DB call decomposed into read-modify-write so concurrent orders oversell.
The headline metric
Pair uplift, measured in both directions: what did B catch that A missed, and vice versa. Reported separately because it's asymmetric.
His demo numbers
Reviewer A: 50% recall. Reviewer B: 58.3%. Together: 91.7%. They overlapped on only 2 of 11 finds. But note the last 8.3%: one bug — a missing header crash — both reviewers missed entirely. His own demo demonstrates his own limitation: two models agreeing is not two models being right.
Reality check
Those numbers are hand-authored and labelled SIMULATED in the title, the report and the JSON. They're a designed demo, not evidence. He is scrupulous about saying so.
His limitation, verbatim: "Do not say 'model B is better' from this corpus alone. A defensible statement is narrower: 'On this 12-defect synthetic corpus, under the recorded setup, B added N planted defects that A missed.'" — and one of six integrity rules: "Never describe a simulated, hand-authored, incomplete, or ground-truth-exposed run as measured model performance."
loss-weighted-unknowns
2/2 testsv1.0.0

Rank your open questions by what being wrong would cost — not by how uncertain each one feels. Uncertainty and importance are different things.

The formula
priority = severity × likelihood × irreversibility × blast-radius × compliance-exposure. Each 1–5, so scores run 1 to 3125. Multiplied, not added — deliberately, so a question that's severe and irreversible and broad dominates a merely vague one.
The whole argument, in his numbers
"Will customers understand the button label?" has likelihood 5 — the highest in his set, and scores 20 (dead last). "Can the settlement ledger mapping be corrected after release?" has likelihood 3 and scores 1200. Sorting by uncertainty puts button copy first. That inversion is the entire point.
The distinction that matters
Stated twice: "Score likelihood of the harmful outcome, not confidence in the answer." Confusing those two is the exact failure the tool exists to prevent.
Nice touch
Ties are shown, not broken by a fudge factor. Two of his examples genuinely tie at 1500.
Reality check
Every number is a human's guess. It's a calculator and a sorter — it discovers nothing.
His limitation, verbatim — note he names his own central mechanism as the weakness: "Scores are judgments. Teams can anchor poorly, inflate pet risks, confuse likelihood with uncertainty, or hide disagreement behind a number. Multiplication also implies interactions and precision that the evidence may not support."

Human & memory

3 tools · keeping you in the loop

The family most relevant to you, and the one least about code.

quiz-me
Prompt-onlyv1.0.0

Your agent examines you on the code it wrote for you. Eight questions, graded honestly, no flattery.

Problem
Stated bluntly: "Agents write the code; you stop being able to answer for it."
The 8 questions
3 × "why is it built this way?" (design intent, rejected alternatives) · 2 × "what breaks if X fails or doubles?" · 1 × "where does this number come from?" (constants, thresholds, prices) · 1 × "walk me through what happens when…" · 1 wildcard: "whatever would embarrass the human in a due-diligence meeting."
Scoping
Last 7 days of commits or last 5 merged PRs, whichever is richer. Prioritises "anything touching money, auth, persistence, or external APIs." Skips formatting noise.
The grading rule
"No grade inflation. A wrong 'why' is wrong even when the 'what' was right." Verdicts are correct / partial / missed. Below 6/8 you get a retake.
Delivery
One question at a time. Wait for the answer. Do not hint. Then re-explain every miss with file paths.
Install
npx skills add runsagents/quiz-me, then say "quiz me." Or paste the raw URL — zero install.
Reality check
The entire engine is ~35 lines of prompt. "Honest grading" is enforced by four imperative sentences and nothing else. There are no evals proving it resists flattery.
His own practice, verbatim: "I run this weekly on my own fintech, where agents write most of the code... Below 6 of 8, I study and retake. The product isn't mine until I pass." — He cites real research: Anthropic found AI-assisted developers scored 17% lower on comprehension quizzes, "the equivalent of nearly two letter grades."
voice-calibration
Template onlyv1.0.0

Turn ten years of your own chat history into a style guide, so "draft this in my voice" finally means something.

Problem
"Every AI draft 'in your voice' sounds like LinkedIn. This is the method that fixed mine, my agent now drafts messages my friends can't flag, down to the punctuation quirks."
The method
1. Export your corpus — "chat exports beat polished writing, because your real voice lives in the unedited stuff." His was 43,252 Telegram messages over ten years. 2. Extract patterns, not content. 3. Write a style guide and correct it. 4. Blind-test until it passes.
The four-part guide
Keep-list (quirks that ARE you — keep them even if "wrong") · Fix-list (typos, autocorrect damage) · Anti-patterns (corporate filler dies here) · Calibrated exemplars (full messages you approved).
Best idea in it
"Your 2016 voice is history, not identity." Voice is dated; the guide anchors to one era. And the stopping rule: "Stop when you hesitate before spotting your own."
Relevant to you
Step 2's first extraction target is "which languages you mix and when" — code-switching is a first-class feature, and language is a required parameter. This method was plainly designed by a multilingual author.
Reality check
The repo ships no working prompt — only a fill-in-the-blanks template and four paragraphs of method. You build the analysis yourself. And 43k messages won't fit in a context window; step 1 is secretly a data task.
His privacy note, verbatim: "The corpus never needs to leave your machine, point a local agent at it. The finished guide contains patterns, not messages, but it's still a fingerprint of you: treat the guide itself as personal data, and don't publish it." — Note the gap: his own template requires "full example message, approved verbatim", so the guide does contain real messages. And "never leaves your machine" is only true with a local model — pointing Claude at a Telegram export sends every message to the provider.
memory-ledger
9/9 testsv1.0.0

Every stored memory must say where it came from, when it dies, and whether it's allowed to authorise an action.

Problem
"A stale unscoped memory can outlive an approval and trigger the wrong consequential action." His framing: "Memory is convenient in prototypes; at production stakes, unqualified memory is hidden state."
Required fields
fact (one atomic claim) · source.kind (user-said / observed / inferred) · source.reference · scope · confidence · created · exactly one of expires or review-by · superseded-by · may-this-authorize-action.
The central invention
A field named as a question: may-this-authorize-action. Setting it true triggers four extra rules — the source can't be inferred, confidence must be ≥0.9, scope must be specific, and it must have a hard expiry, not a soft review date. Standing approvals must be re-approved on a calendar.
The demo that lands
His example #2 is a release approval that is structurally perfect — it passes every validation check. It's defeated purely by time: audited two weeks after its expiry, it drops out of the eligible list. Validation alone can't catch it; only a dated audit can.
Reality check
The field list is closed — any extra key is a hard error. You cannot retrofit this onto existing Obsidian notes with tags: or type:. It must live as a separate parallel ledger. Also: the shipped JSON schema is never read by the code.
His limitation, verbatim: "A clean audit is evidence about ledger hygiene, not proof that a fact is true or an action is safe, legal, permitted, or desirable." — and the rule that matters: "The flag never expands the agent's current permissions and never replaces fresh approval."

1 tool · the front door
permission-surface
5/5 testsv1.0.0

Before you run npx skills add something, scan it and see what it could do.

Problem
"A one-line install can hide lifecycle hooks, mutable downloads and writes outside the repository."
Eight signals
Executable files & shebangs · install hooks (postinstall scripts) · network endpoints · shell execution (curl | sh, eval, child processes) · writes outside the repo · secret-looking strings · mutable-ref fetches · declared-vs-observed capabilities.
Best concept
Mutable ref — code fetched from main or latest rather than a pinned commit. His framing: "A mutable fetch asks 'what content will arrive later?'" You reviewed one thing; you'll run another.
Honest by design
The disclaimer is embedded in every report, not footnoted. "QUIET means no v1 heuristic matched, not that the artifact is safe."
Reality check
Regex, not real analysis. Trivially evadable — string concatenation defeats it in one line. It catches careless, not hostile. And see the bug table: it produces false alarms on ordinary Markdown.
His limitation, verbatim (bolded in his original): "This is a static heuristic scan. It has false positives and false negatives, does not execute code, resolve indirection, inspect fetched content, model every language or installer, or prove whether a behavior is reachable. It is not a security audit and makes no 'safe' or 'malicious' determination."

The habit worth stealing above all others

Each repo names its own central mechanism as its own weakest point. That is rare enough to be worth listing:

  • loss-weighted-unknowns sells you on multiplying five scores — then says "multiplication implies interactions and precision that the evidence may not support."
  • handoff-receipts ships a validator — then says "validation is not proof" four separate times.
  • permission-surface is a security scanner that refuses to say anything is safe.
  • second-opinion-bench exists to test whether second-opinion — his own product — is worth the money.
  • second-opinion-bench's demo shows a reviewer pair scoring 91.7%, not 100% — his own numbers prove his own caveat that agreement isn't proof.
The transferable lesson

A tool that states its own limits is more trustworthy, not less — because you know where the edge is. This is the opposite of how most tools are marketed, and it's the highest-quality thing in the entire collection. It costs nothing to copy and it's worth more than any of the code.

The honest read

This is a very good thinker's first public draft, shipped fast and documented far better than it is proven. The ideas are strong and several are genuinely valuable to you. The code is small, clean, and mostly beside the point — the doctrine is the asset.

Do not treat it as a mature toolkit to install wholesale; it isn't one, and he doesn't claim it is. Treat it as a well-argued curriculum. The right move is to read the five or six that apply to you, take the rules, and install almost nothing. CC0 means there's no cost to doing exactly that.

The single best thing here

Not any tool. It's the framing: as agents write more, the bottleneck stops being agent output and becomes whether a human still understands enough to be accountable. Every one of his 13 tools refuses to decide — they gather evidence and hand it to a person. That is the whole design, and it's correct.

His sharpest line, from night-watch, is the one to remember: an unattended agent that fixes what it doesn't understand leaves you with a system that is "internally consistent and more wrong."
